# 運用設計書

文書ID：OPS-01／版：1.0／作成日：2026-10-29／状態：レビュー用・実施記録からの事後整理。

Day 1〜4の起動・停止、監視、配備、バックアップ復元、障害演習、終了処理を横断して整理する。実施済みの運用と、今後継続運用する場合の手順・担当案を区別する。24時間の監視体制や顧客との運用合意を取得した文書ではない。

関連資料：[要件定義](requirements.md)／[基本設計](basic-design.md)／[詳細設計](detailed-design.md)／[試験仕様・結果](test-specification-results.md)／[文書索引](README.md)。設定値の正本は公開コードと対象段階の実行記録とする。

## O01 運用目的と対象

目的は、正常性を実応答で確認し、異常の検知から切り分け・復旧までの手順を説明できること、変更を追跡できること、元データと証跡を守りながら不要な支出を抑えることである。

| 対象 | 運用範囲 | 実績の境界 |
|---|---|---|
| Day 1基盤 | EC2・OS・Apache/Tomcat/PostgreSQL・EBS/EFS/S3・SSM・Agent | 再起動・永続性・ログ到着・停止を確認 |
| Day 2追加構成 | Backup・復元領域・内部ALB/NLB・アクセスログ・5xxアラーム | 元DBとは別領域で復元確認。SNSは未接続 |
| Day 3追加構成 | GitHub・CodePipeline/CodeBuild・ECR・ECS・ALB・API | 自動配備と実API応答まで確認。DB接続・CodeDeployは未実施 |
| Day 4追加構成 | SNS・Step Functions・単発ECS・EventBridge・監視 | 成功/失敗・定期起動・Tomcat障害・停止通知を確認 |

各段階の追加構成は検証後に撤去した。常時稼働する一つの環境ではない。最後の記録ではEC2停止、元EBS/EFS・スナップショット・S3証跡・共有ロール等を保持している。空のDay 2 Backupプランは対象割当なしで残る。現在の状態を再確認せず、記録時点の状態を現在保証と表現しない。

## O02 役割・連絡・対応時間

以下は個人検証向けの役割整理である。同一人物が複数役を担い、実務での分業・当番体制は未整備。

| 役割 | 責任・判断 |
|---|---|
| 環境所有者 | 費用・公開範囲・権限・元データの削除可否を判断。認証・メール購読を確認 |
| 作業担当 | 開始点検、監視、変更、切り分け、復旧、終了確認と記録 |
| レビュー担当（実務導入時に割当） | plan・影響・試験・切戻し案と完了結果を確認 |

本検証の連絡手段はSNSメール。通知先の実アドレスと連絡先一覧は非公開台帳で管理する。受付時間、夜間対応、一次応答期限、エスカレーション先と期限、SLA・RTO/RPOは未合意である。

障害対応で権限追加・費用増・データ上書きが必要な場合、影響と代替案を示して環境所有者の判断を受ける。診断目的で機密情報を公開リポジトリへ掲載しない。

## O03 運用作業と実施契機

頻度は今後の再検証時の運用案。毎日・毎週継続して実施した実績を意味しない。

| 契機 | 作業 | 完了条件・残す記録 |
|---|---|---|
| 作業開始時 | 認証・リージョン・対象資源・保存対象・課金対象を照合 | 対象と差分を台帳で確認 |
| 起動後 | SSM・サービス・マウント・HTTP/SQL・ログ確認 | O04の正常性確認を満たす |
| 検証中 | アラーム・ジョブ失敗・実応答・タスク状態を確認 | 異常を未解決のまま完了扱いしない |
| 変更ごと | コード・plan・試験・実応答を照合 | 対象コミットと配備内容が一致 |
| バックアップ検証時 | ジョブ完了後、別領域で復元内容を確認 | SQL・ファイル内容が一致 |
| 作業終了時 | 一時スケジュール無効化、追加分整理、EC2停止、証跡保全 | AWS実在とstateを照合 |
| 請求反映後 | 残存保存領域と請求を確認 | 対象外費用を区別して記録 |
| 再検証前 | 認証期限・イメージ・依存サービス・通知先を再確認 | 前回の成功に依存せず実行条件を満たす |

## O04 起動・正常性確認・停止

### 起動手順

1. 認証とap-northeast-1を確認し、タグだけでなく非公開台帳の対象IDを照合する。認証切れを権限不足と混同しない。
2. 元EC2を起動し、状態チェック・SSM Onlineを確認する。停止・起動で変わり得る公開IPを固定前提にしない。
3. `findmnt`等でDB EBSとEFSを確認する。DB用マウントがない場合はDB書込み試験を進めず、デバイス・UUID・fstab・権限を調査する。
4. httpd・tomcat・postgresqlのactive、待受、SELinux Enforcingを確認する。認証情報を画面出力しない。
5. Apache経由の/portfolio/でHTTPと検証行を照合する。SSMからの内部確認またはポート転送を使う。
6. Agent・対象ログ・メトリクスを確認する。追加構成を使う場合は各段階のTerraform手順で再作成し、LB/API/バッチも別途確認する。

正常の判定はEC2 runningだけでなく、マウント・サービス・HTTP本文・SQL・監視到着を組み合わせる。Day 3はDB未設定のリリース表示を期待値とし、Day 1と同じDB試験にしない。

### 一時停止手順

アプリ確認と証跡回収を終え、一時スケジュールを無効にし、実行中タスク・配備・バックアップの状態を確認する。SSMセッションを終了し、対象EC2を停止してstoppedを確認する。DB EBSのスナップショットを取得する場合は、正常停止後に対象を照合しcompletedまで確認する。Day 4の停止イベント通知も試験する場合、通知資源は受信確認まで残す。

起動・停止の具体操作は[Day 1手順](../../terraform/README.md)と段階別の手順に従う。手動変更を行った場合は次回planで差分を確認する。

## O05 監視・通知運用

閾値・期間・欠損値の詳細は[詳細設計D12](detailed-design.md#d12-ログ監視閾値)を参照。

| 監視対象 | 検知内容 | 通知・実演範囲 |
|---|---|---|
| EC2 CPU | >80%、300秒×2 | Day 1はSNSなし。Day 4はALARM通知設定、超過実演なし |
| メモリ | >85%、60秒×2 | Day 1の指標・アラーム。SNSなし |
| root/DBディスク | >80%、60秒×2 | Day 1はSNSなし。Day 4はrootのALARM通知設定、超過実演なし |
| StatusCheckFailed | >0、60秒×2 | Day 1の設定。SNSなし |
| ALBターゲット5xx | Sum >0、60秒×1 | Day 2は状態確認。Day 4はALARM・OKメール実受信 |
| バッチ | 終了コード0／非0・起動/実行例外 | Step Functions結果とSNS通知を照合 |
| EC2停止 | 対象インスタンスのstopped | EventBridge→SNS実受信 |

OS・アプリログとDay 3/4のログ保持は7日。Day 2のALBアクセスログは非公開S3へ保存する。7日を越える長期保存や監査改ざん防止は未設計である。

SNSは購読済みであることを確認する。Publish成功だけでメール到達と判定しない。未着時は購読状態・迷惑メール・通知先・トピックポリシー・SourceArn/SourceAccount・アラーム通知先・配信指標を確認する。通知の自動再送・当番呼出し・確認応答管理は未実装。

アラームは評価期間と欠損値の扱いに影響される。HTTPが復旧してもOK通知が遅れることがある。Day 4 IaCではALARM11:31:05、アプリ復旧確認11:34:45まで、OK11:43:05であり、通知時刻だけから停止時間やRTOを算出しない。

## O06 バックアップ・復元運用

対象はDB EBSとEFS。Day 2では日次・7日保持のプランを設定し、オンデマンド取得と別領域への復元を実施した。検証後は対象割当と今回の復旧ポイントを削除しているため、現在も日次バックアップが継続中とは扱わない。

1. 元データと取得時点を記録する。DB EBSはEC2正常停止後に取得する。
2. バックアップジョブの完了・対象・暗号化を確認する。失敗時はロール、KMS、対象状態、ジョブ理由を調べ、成功前に元資源を変更しない。
3. EBSは同一AZの別暗号化ボリュームへ復元する。NVMeの識別を行い、XFSの重複UUIDを考慮して別パスへnouuidマウントする。mkfsは禁止。
4. 一時PostgreSQLを127.0.0.1:55432で起動し、元DB:5432を維持して検証行を照合する。
5. EFSは別ファイルシステムへ復元し、マウントターゲットとSGを確認して読み取り専用マウント、ファイルをcmp比較する。
6. 一時DB停止・アンマウント後、今回の復元資源を整理する。保持対象の元スナップショットを削除対象と混同しない。

バックアップ成功は復旧成功の代替ではない。リストア実績はあるが、業務データ全体の整合性、時点復旧、7日間の保持動作、RPO/RTO達成は未試験。[Day 2再現手順](../../terraform/DAY2.md)を参照。

## O07 変更・配備・構成管理

変更前に目的、影響対象、対象コミット、plan、試験、切戻し方法を整理する。ソース・設定はGitHub、実値・認証・stateは非公開で管理する。手動変更は理由と結果を記録し、コードへ反映または元へ戻す。

Day 3はGitHub→CodePipeline→CodeBuild→ECSの順で配備する。Source/Build/Deploy各ステージ、ビルドログ、ECRタグ、タスク定義、ALB healthy、公開APIのHTTPとリリース・コミットを確認する。health.jspの200だけでは本体JSPの正常性を保証しない。

失敗時は最後に成功したステージから切り分ける。S3は実プレフィックス`portfolio-day3-pipel/`と実行主体を確認し、広い権限を付けて一時的に通す処置にしない。DockerスモークテストはHTTP失敗と本文不一致をビルド失敗にする。

切戻し案は、確認済みの変更をrevertして再ビルド・再配備し、旧リリースの実応答を確認する方法とする。実際の切戻し演習は未実施。失敗イメージへの再配備や削除済みECRタグの再利用を前提にしない。ECSタスク定義の更新主体はパイプラインで、Terraformのignore_changesとの分担を維持する。

OS更新・ベースイメージ更新は再検証前の変更として扱い、再起動とHTTP/SQLの確認まで行う。定期パッチ適用・脆弱性スキャン・証明書更新の自動運用は未整備。

## O08 バッチ・スケジュール運用

正常系はforceFailure文字列false、故障演習はtrueで実行する。実行名、開始/終了時刻、ECS終了コード、Step Functions状態、SNS通知を対応付ける。終了42は意図した試験失敗であり、通常バッチの成功として集計しない。

通常設定はrate(1 day)・DISABLED。一時的な1分周期を有効にする場合は、変更差分、実行回数、無効化を確認する。1分周期での実行成功を24時間の日次運用実績とはしない。

実行失敗時はエラーとタスクログを保全し、重複実行の影響を確認してから手動再実行する。現行バッチは検証用の出力処理であり、業務データ更新の冪等性・排他・締切・再試行回数は未設計。定期起動を止めても実行中ワークフローが終了したとは判断せず、別に状態を確認する。

## O09 障害対応

通知受信→対象と影響確認→証跡保全→切り分け→復旧→実応答確認→記録の順とする。サービス再起動を繰り返して原因を隠さない。データ破損や対象不明の場合は変更を止め、元領域を保護して所有者へ判断を求める。

| 症状 | 確認順序 | 復旧・終了の判断 |
|---|---|---|
| SSM接続不可 | 認証期限、EC2状態、ロール、Agent、IGW経路・送信 | SSM Onlineと接続成功。別途SSH開放を自動対応にしない |
| HTTP 502/503・5xx | API→VPC Link→ALB/TG→SG→Apache/Tomcat、error_log | サービス修復後に実本文・DB・healthyを確認 |
| JSP 500 | Tomcatログ、JSPコンパイル、設定権限、DB | 修正版スモークテストと実URLで200。healthだけでは終了しない |
| DB起動・接続不可 | EBS接続、findmnt/UUID、所有者・SELinux、PGログ・待受 | 正しい領域とSQL確認。DB初期化で解決しない |
| EFS接続不可 | mount target、2049 SG、NFSクライアント・経路 | 既存ファイル読出し確認。新規空領域で代替しない |
| パイプライン失敗 | ステージ・主体別ログ、S3実パス、ECR、PassRole | 権限/コード修正後、配備から実応答まで再確認 |
| Fargate起動失敗 | 停止理由、イメージ・実行ロール、通信、ログ、health | タスク安定と実応答。タイムアウトだけで原因断定しない |
| 監視データなし | Agent、ログ、権限、メトリクス次元、反映遅延 | データ到着確認。欠損を正常と決め付けない |
| 通知未着 | O05の購読・発行元権限・受信側確認 | 対象通知の実受信。Publishのみで完了しない |

Tomcat停止演習ではSSMスクリプトにEXIT trapによる起動処理を入れる。復旧後、httpd/tomcat/postgresqlのactiveとHTTP200・検証行を確認する。再起動処理自体の成功も確認し、trapだけで復旧保証としない。

障害記録には発生・検知・対応・復旧時刻、影響経路、現象、原因の確度、処置、確認結果、残課題を残す。Day 3の一度のヘルスチェックタイムアウトはタスク置換後の正常性を確認したが根本原因未確定であり、原因解決済みと記載しない。

## O10 権限・秘密情報・証跡管理

管理接続はSSM、EC2はIMDSv2、SELinux Enforcingを維持する。アプリDB接続ファイルはroot:tomcat・0640。秘密値・実ID・メール・APIキー・state・plan・実値tfvarsを公開GitHubへ置かない。通知内容・エラーログにも秘密値を含めない。

実作業ではroot認証を使用した箇所がある。今後の実務運用ではフェデレーション等による作業者識別と最小権限の運用ロールへ分離する必要がある。権限棚卸し・鍵更新・監査体制は未整備で、実施済みとは扱わない。

公開証跡は対象段階、コミット、実行日、期待値と結果が分かる要約にする。原本はアクセスを限定して保持するが、保管期限・監査上の要件は未合意。Day 1中心の[既存運用手順](../operations.md)は履歴資料として残し、Day 2〜4の復元・通知実績は本書と各実施記録で補う。

## O11 停止・撤去・費用管理

終了前に「追加検証資源」と「元データ・共有資源」の一覧を作る。タグは補助に使い、タグ一致だけで一括削除しない。以下は実施記録を基にした終了方式であり、本書追加時にAWSの削除操作を実行したものではない。

| 範囲 | 終了方式・注意点 |
|---|---|
| Day 2 | 同じ基盤stateの追加フラグだけを無効化。LB/TG・復元EBS/EFS・今回の復旧ポイント・対象割当・一時アラーム等を整理。基盤全体destroy禁止 |
| Day 3 | 専用stateの26管理資源を削除。パイプライン登録の動的タスク定義も対象を照合して整理 |
| Day 4 | 一時スケジュール停止・実行確認後、専用stateの24資源を削除。所有するタスク定義の補助削除も確認 |
| 元基盤 | EC2停止、元EBS2・EFS・元スナップショット・S3証跡を保持 |
| 共有資源 | 既存実行ロール、GitHub接続、AWSの同期待機用標準ルール、他学習資源を追加分と混同しない |

stateが空でもAWSに動的資源が残る場合がある。最終planとAWS実在一覧、EC2 stoppedを併せて確認する。元データの最終廃棄は保管要件・復元必要性を別に判断してから行う。

EC2停止後もEBS・EFS・スナップショット・S3等の費用は残る。Budgetsは費用通知であり強制停止ではない。請求反映の遅延、タグ未配賦、他学習分を区別する。Day別の確定費用は未算定で、当初予算・残クレジットを実績額に置き換えない。
