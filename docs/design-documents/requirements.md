# 要件定義書

文書ID：REQ-01／版：1.0／作成日：2026-10-29／状態：レビュー用・事後整理。

本書はDay 1〜4の実績を基にした**学習環境の整理要件**です。構築前の顧客ヒアリングや承認記録を示すものではありません。[全体索引・対応表](README.md)を参照してください。

## 1. 背景と目的

従来のRHEL上のApache・Tomcat・PostgreSQL構成を出発点に、AWSでの保存・復元・負荷分散・コンテナ配備・運用自動化を段階的に検証する。サービスの作成だけでなく、設計理由、実応答、不具合修正、再現、終了処理を説明できる状態を目指す。

業務システムの売上・顧客数等の事業効果は定義していない。利用データは検証用のメッセージ・ファイル・リリース表示であり、顧客の業務データを処理する要件ではない。

## 2. 関係者と利用場面

| 役割 | 利用場面・責務 |
|---|---|
| 学習環境の所有者 | AWS利用範囲、支出、認証・購読確認、保存データの扱いを判断する |
| 構築・運用担当 | 設定、実行計画の確認、配備、監視、障害切り分け、復旧、削除を行う |
| レビュー担当 | 要件と設計・コード・試験結果の対応、未実施範囲を確認する |
| 検証クライアント | SSM経由または検証用公開APIから画面を呼び出す。一般利用者の本人認証は未実装 |

作業にはAI支援を利用した。構築判断や検証内容を自身で説明できることを、ポートフォリオ利用時の前提とする。

## 3. 対象範囲

| 段階 | 対象 | 対象外・留意点 |
|---|---|---|
| Day 1 | VPC、RHEL EC2、Apache/Tomcat/PostgreSQL、EBS/EFS/S3、SSM、基本監視 | EC2は1台。WebとDBが同居 |
| Day 2 | AWS BackupのEBS/EFS復元、内部ALB/NLB、アクセスログ、5xx検知 | Aurora作成・DB移行・複数ターゲット間切替は未実施 |
| Day 3 | ECR、CodeBuild、CodePipeline、ECS Fargate、内部ALB、API Gateway | CodeDeploy実行・コンテナDB接続は未実施 |
| Day 4 | ECSバッチ、Step Functions、SNS、EventBridge、監視・障害復旧 | 業務バッチ、長期間の定期運用、常駐ECSの性能監視は未検証 |
| IaC | Day 1取り込み、Day 2〜4の対象範囲の再現・試験・終了 | 空アカウントから全段階を無操作で一括構築した実績ではない |

## 4. 機能要件と受入条件

優先度「必須」は今回の学習範囲内の位置付けであり、本番案件の契約上の優先度ではない。

| ID | 整理要件／優先度 | 受入条件 | 実績 |
|---|---|---|---|
| FR-01 | Web画面からDBを参照する／必須 | JSPの応答とPostgreSQLのSELECT結果が一致する | Day 1/2で確認。Day 3コンテナは対象外 |
| FR-02 | 保存用途を分離する／必須 | DBは追加EBS、共有ファイルはEFS、成果物・ログは非公開S3へ保存できる | 確認済み |
| FR-03 | 元データを上書きせず復元する／必須 | 別EBSの復元DBでSQLを取得し、別EFSのファイルが元と一致する | Day 2で確認 |
| FR-04 | L7/L4転送を比較する／必須 | 内部ALB/NLBから同じDB由来の画面を取得できる | Day 2で確認。冗長化の証明ではない |
| FR-05 | WARとコンテナを生成し配備する／必須 | 実画面のスモークテスト後にECRへpushし、ECSで画面を返す | Day 3で確認 |
| FR-06 | 変更を起点に自動配備する／必須 | 対象コミットのSource/Build/Deploy成功と新リリース表示が一致する | コンソール・IaCの両方で確認 |
| FR-07 | API経由の検証経路を提供する／必須 | 実エンドポイントでキーなし403、あり200と期待する本文を確認する | Day 3で確認。キーは利用者認証ではない |
| FR-08 | バッチの完了と失敗を通知する／必須 | 終了コード0/42を実行し、ワークフロー結果・SNS発行・メール受信を照合する | Day 4で確認 |
| FR-09 | スケジュール・イベント起動を行う／必須 | 自動起動の入力と完了を確認し、対象EC2の停止通知を受信する | Day 4で確認。日次設定の24時間反復は未試験 |
| FR-10 | 監視・障害復旧を検証する／必須 | OS指標・ログを確認し、Tomcat停止時の503、5xx ALARM、復旧後の200/DB、メール通知を照合する | 段階別に確認。全指標の閾値超過は未試験 |

## 5. 非機能要件

| ID | 整理要件 | 実装・確認範囲／制約 |
|---|---|---|
| NF-01 | 管理経路と受信範囲を限定する | SSMを利用しSSH受信なし。EC2/ALBのHTTPとDay 3 ECSの8080はVPC内。Day 4バッチ受信なし |
| NF-02 | 保存データ・認証情報を保護する | EBS/EFS保存時暗号化、S3非公開・HTTPS要求。秘密情報とstate等は公開対象外。EFS通信TLS・秘密情報専用サービスは未導入 |
| NF-03 | 再起動後の永続性を確認する | サービス自動起動、UUIDによるEBS、EFSマウント、DBデータを実測。すべての障害パターンを保証しない |
| NF-04 | 同じ対象範囲をIaCで再現する | 段階別state/フラグ、構文検査、保存したplan、apply後の実測と差分確認を用いる |
| NF-05 | 不使用時の費用発生を抑える | 検証追加分を削除、EC2停止。元の保存領域等は保持し、継続料金をゼロと扱わない |
| NF-06 | 変更と検証根拠を追跡する | GitHubコミット、ビルド情報、リリース表示、実行履歴、要約証跡を対応付ける |
| NF-07 | 可用性・性能を過大に保証しない | 学習用途の単一EC2。2 AZのサブネット/LBをアプリ冗長化の達成と扱わない。SLA、同時数、応答時間目標は未定義 |
| NF-08 | 費用情報の範囲を明示する | 課金資源と終了状態を記録。アカウント全体表示をこのポートフォリオ単独の確定費用としない |

## 7. 前提・制約・運用境界

1. リージョンは東京。作業記録のFreeプラン維持方針に従った。Auroraを保留した判断は当該アカウント・時点の観測であり、現在の全AWSアカウントの仕様を断定しない。
2. 段階の構築・検証に必要な権限と既存基盤があること。実施時には利用者の指示によるrootセッション使用があり、日常運用の理想設計とは分ける。
3. 既存のDB/EBS/EFS/S3・共有ロールや他の学習資源を一括削除しない。
4. Day 3/4では、既存の認証済みGitHub接続・ECS実行ロール等を参照する。完全自動化のために対話的な認証をコードへ埋め込まない。
5. 作成・削除・通知には非同期処理と反映遅延がある。完了状態と実応答を別々に確認する。

## 8. 未定義事項・本番適用前の確認票

| 項目 | 今回の扱い | 業務案件で決める内容 |
|---|---|---|
| 可用性・保守時間 | 数値未定義 | 稼働率、メンテナンス時間、冗長化対象 |
| RTO/RPO | 未定義・達成試験なし | 業務影響、許容損失、復旧期限、復元頻度 |
| 性能・容量 | 負荷試験なし | 同時利用数、TPS、応答時間、データ増加量 |
| 利用者認証 | 未実装 | IdP、認証方式、認可、セッション管理 |
| 通信暗号化 | 公開APIのHTTPS以外は限定的 | EC2/ALB/EFS/DB各経路のTLS、証明書管理 |
| 運用体制 | 個人検証 | 連絡先、一次対応、承認、夜間対応、権限分離 |
| 予算と配賦 | 単独確定額未集計 | 月次上限、通知基準、配賦タグ、クレジット超過時の対応 |
| 監査・保管 | 長期監査要件なし | 保存期間、改ざん防止、監査ログ、法令・組織基準 |
