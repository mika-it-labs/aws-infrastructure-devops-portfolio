# 学びと改善

## 1. 権限不足をサービス単位で把握する

作業用ユーザーではVPCを作成できましたが、IAMロール作成・PassRole・S3作成・EFSタグ操作の権限が不足していました。あるサービスを操作できても、構築全体を完了できるとは限らないことが分かりました。

実施では利用者の指示でroot認証を使用しました。再実施に向けては、管理者が必要な作成・タグ・PassRole権限を作業用ロールへ設定し、EC2自身のロールと構築者のロールを分けることが改善点です。

## 2. 軽量なEC2では初期更新時間も設計に含める

RHELの初期更新では多数のパッケージとSELinux・カーネルの後処理が必要でした。t3.smallのCPUクレジット設定をStandardにしていたため、途中だけUnlimitedに変更し、終了前に戻しました。常時稼働だけでなく初期構築時の負荷・所要時間・追加料金も確認する必要があります。

## 3. ストレージは起動直後の成功だけでは判断しない

追加EBSをAWSのボリュームIDとSERIALで照合し、UUIDでfstabに記録しました。再起動後のマウント・DBデータを確認することで、実行中だけ成立する設定を避けられました。スナップショット作成は確認しましたが、復旧可能性の実証にはリストア試験が必要です。

## 4. 設定と動作の証跡を分ける

Agentの設定完了だけでなく、CloudWatchのログイベントと指標の出現を確認しました。一方、アラームを作成しただけではSNS通知まで証明できません。実施した確認と未実施の確認を分けて記録することが重要だと学びました。

## 5. 公開用資料は実行環境のコピーにしない

実行台帳にはアカウントID・ARN・IP・リソースIDが含まれます。公開版は必要な証跡を選び、識別子を置換しました。実データの原本は別に保持し、公開版のサンプルコードと実行済み版の違いも明記しています。
